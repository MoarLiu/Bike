整理日期：2026-11-09（Asia/Shanghai）

**状态更新于 2026-11-10，R01–R14 开发及本机验收完成，正式版封版为 2.0.0。真实 AI/MCP 接入和两台物理设备验证由用户后续补测。** 用户确认将原 1.8.0“AI 与 MCP 闭环”和原 2.0.0“多设备自动合并”合并开发，正式发布目标统一为 **2.0.0**，不再单独发布 1.8.0。开发按架构验证、alpha.1、alpha.2、alpha.3、beta 和正式版分阶段推进。

本计划是合并后的现行依据。[原 1.8.0 计划](development-1.8.0.md) 仅保留历史细节；其中“不做节点合并/附件同步”、独立里程碑及旧工时估算不再适用于本版。实现和测试证据见 [实施记录](implementation-2.0.0.md)、[验收记录](acceptance-2.0.0.md) 及 [制品验证](publish-verification-2.0.0.md)。

## 1. 目标、基线与复用原则

版本主题：**AI 知识工作流与个人多设备同步**。继续以 Electron macOS、本地优先、个人使用为边界：AI 和 agent 可受控整理知识，个人的多台设备能够安全交换和合并内容。

依据为 [路线图](roadmap.md)、[1.7.0 实施记录](implementation-1.7.0.md)、[1.7.0 发布验证](publish-verification-1.7.0.md)、[同步服务](sync-service.md) 及原 1.8.0 的增量拆解。本地 `v1.7.0` 对应源码 `3c90ba6dae23a1688859cada674fff3b29c5efa0`；实际开工从包含该发布源码及必要后续修复的基线建立 `codex/development-2.0.0`，记录实际 commit，不在本次规划中修改应用版本或执行发版。

现有 operation log 仅持久化和分发记录，不等于已有自动合并；现有快照式撤销也不等于跨设备撤销算法。普通历史与正文分属不同 IndexedDB 数据库，不能假定跨库原子提交。

不重建附件库、ZIP、通用版本历史、文件写入锁或全部编辑视图。只抽取新增链路必需的共用部分；回归成本单列，不再把已交付能力重复计入开发。

### 1.2 合并后的范围边界

- 本机编辑、已下载附件和恢复在离线时可用。同步、Live MCP 和外部模型调用分别启用，不互相作为使用前提。
- 新同步能力面向个人多台 macOS 设备；保留现有单用户 Sync Server，不引入多人实时协作、团队、账号体系或新平台。
- Web 维持现有功能、格式兼容与安全维护。新协议下不能安全写入的旧客户端进入受保护状态，不为本版扩展 Web 专属产品功能。
- 原文件 MCP 参数、备份暂停、Sync 文档保护和 v1/v2 导入能力持续维护；Live 断开不能自动转向文件写入。
- 文件夹、XMind 实际导入、Intel/Universal、HTML 分享、全库图谱和模板编辑器不纳入本次合并范围。
- 正式签名、公证及原生自动升级继续独立跟踪。沿用已确认的 arm64/ad-hoc 边界；本计划不把签名链路描述为已完成，也不重做现有检查/下载流程。

## 3. M0：先验证共同基础

### 3.1 必须先形成结论的决策

| 决策 | 验证内容 | 冻结出口 |
| --- | --- | --- |
| 合并机制 | 对比适合现有树形数据的成熟合并库与基于共同基线的合并方案；沿用路线图中的 Yjs/Automerge 等候选，不预先锁定 | 用同一组并发样例比较正确性、迁移量、包体/性能及维护成本，选定一条实现路线 |
| 操作与排序 | 文档/主题 id、父子关系、稳定排序、移动、删除、恢复及并发插入 | 确定合法操作、结构约束和冲突语义；不能仅凭数组下标定位 |
| 持久化边界 | 正文、操作状态、恢复引用、outbox 与接收游标的一致性 | 崩溃后无已显示成功但丢失的写入，无重复应用 |
| 同步协议 | 日志提交、去重、游标、checkpoint、能力协商、旧客户端隔离 | 冻结版本化契约和升级顺序，不把现有 log API 原样当成合并协议 |
| 撤销与恢复 | 本机撤销、远端修改、AI 批量操作、历史恢复分别验证 | 撤销不抹掉远端更新，恢复生成可传播的新操作 |
| 新旧格式 | 是否提升 Workspace/IndexedDB/导出格式及最小可写版本 | 明确迁移、备份、失败回退、旧端拒写和导出范围 |
| Live 通道 | stdio 经本机受保护通道接主进程与可信 renderer | 正式包、授权、重连和窗口生命周期原型通过；只实施一种传输路线 |
| 附件传输 | 复用内容哈希，验证服务端对象安装、续传与配额 | 正文与二进制分别显示进度，完整状态有可核验标准 |

M0 必须跑两个隔离客户端的真实数据流程：不同节点改字、同字段冲突、同位置插入、并发移动、删除对编辑、离线重连、重复/乱序消息、远端修改后的本机撤销。先固定语义，再扩展菜单和模型能力。

无法证明能正确处理的结构冲突应保留各分支并进入显式冲突处理，不得为达到“自动合并”而默默丢失内容。M0 的方案和实测记录另存实施文档，不在本计划中编造测试结论。

### 3.2 三类记录共用关联，不混成一种日志

| 层次 | 保存什么 | 边界 |
| --- | --- | --- |
| 待确认提案 | 读取基线、目标、候选命令、依赖组、差异摘要、有效期 | 尚未修改正文，不进入其他设备的正式操作流 |
| 已提交操作 | 操作 id、来源、作者设备、目标、因果/基线信息、变更内容和批次关系 | 由选定合并机制编码和复制；仅重试传输不能再次执行 |
| 本机审计/恢复记录 | 用户原因、客户端/模型/模板来源、确认结果、前后摘要、恢复点 | 关联已提交操作；API key、令牌、完整 prompt 和本机路径不进入同步 |

一个用户确认可形成一批节点操作。审计按这次确认归组，同步按选定协议可靠传输；这些是同一修改的不同表示，不能让 UI、AI、MCP 和同步各自生成不一致的正文。

操作身份不能只依赖时间戳；设备/副本身份、重试 id 和批次 id 需要稳定且可去重。导入副本、迁移设备和恢复备份时明确哪些身份保留、哪些必须重建，避免两台设备误用同一个副本身份。

### 3.3 本机提交与远端接收

- UI、应用内 AI、Live MCP 和远端操作接收汇入同一文档操作入口；只为相关入口作必要改造，不重写所有视图。
- 本机确认先刷新可提交草稿，检查权限、目标、提案基线和资源预算，再形成候选状态。
- 正文更新、操作回执、必要恢复数据和 outbox 在可证明的一致提交边界内完成。优先扩展现有 `bike-db` 事务，不假定正文库和历史库可跨库原子提交。
- 本机成功回执表示已经持久保存，允许处于“待同步”；不能等同于远端或附件已经同步完成。仅 localStorage 备用保存不能冒充完整 AI/Live 事务成功。
- 远端操作经校验和合并后，正文、已应用集合及接收游标一并持久化；崩溃重播不重复创建节点。
- 内容提交后统一刷新 UI、索引、链接和关系，再触发已有自动备份。新桥不得自行绕过备份队列双写 iCloud。
- 同一请求 id 与相同内容返回原结果；相同 id 携带不同内容拒绝。回执丢失时先查询，已过期结果不能被当成安全重做依据。
- 网络、附件文件 I/O、模型请求和用户确认不放进 IndexedDB 或 SQLite 的长事务中。

### 3.4 AI 预览与同步合并的关系

自动合并已经提交的个人设备操作，不替代用户对 AI 提案的确认。

- 预览绑定工作区、目标 id、读取基线、规范化命令及提案摘要。目标内容在等待期间变化，提案进入过期状态，重新比较后才可确认。
- 首版可保守地使整个目标文档变化触发重新预览；只有能证明影响无关时才缩小失效范围，不把细粒度优化设为首版前提。
- 选中组提交前再次校验；父节点新增与子节点、节点合并与引用改绑等依赖不可拆开。
- 一次“应用所选修改”形成一个本机撤销步骤；未接受内容不修改正文。
- 生成期间保持可编辑、可取消；切换文档后仍绑定原目标，不能将结果写到当前选择。
- 同步接收和用户确认竞争时通过提交协调器串行决定本机状态；已批准提案不得在目标改变后无提示重算成另一组修改。

### 3.5 撤销、恢复和冲突处理

- 普通本机编辑及 AI 批次沿用现有撤销入口，补齐新建文档的撤销/重做。
- 同步启用后的撤销产生针对本机操作的补偿/逆向变更，具体实现随合并机制冻结；不能恢复整篇旧快照来覆盖其他设备的新内容。
- 同一字段被后续远端修改时，保留当前值并提示冲突或选择恢复为副本。恢复不是绕过并发校验的后门。
- 历史恢复保留恢复前状态，并产生新的可同步操作；操作 id、同步游标和设备时钟不倒退。
- 冲突解决本身也有来源、版本基线、幂等标识和同步记录。解决期间再次收到冲突相关修改则重新比较。
- 多文档改名/合并的引用改绑按可核验批次处理；接收端不能将一半结果标为已完成。事务范围、暂存和失败处理在 M0 冻结。
- 恢复记录复用已有历史能力，显示实际保留/过期状态。新增记录及 outbox 的附件引用加入现有清理根。

## 4. 工作包与验收

所有工作包均属于合并版本。W01/W02 是共同基础；W03–W05 对应原 1.8.0 的主要增量；W06–W09 对应原 2.0.0；W10/W11 负责兼容和证据。各包中的“复用”和“新增”分别计量。

### W01 操作模型、合并原型与稳定排序

复用现有主题 id、树命令、知识连接和 MCP 写入规则。

- 定义当前编辑动作与可同步变更之间的映射，覆盖标题、正文、备注、任务、格式、表格/代码、插入、删除、移动、链接和关系。
- 稳定排序支持同位置并发插入与移动，结果在各副本一致；不以每次重写全部数组顺序作为默认操作。
- 进行 M0 合并机制原型，验证树无环、单一父级、id 唯一、孤儿处理及引用保真。
- Markdown 与树的互转保持既有身份；无法逐字段安全映射的修改按明确批次和冲突边界处理，不偷偷换 id 或静默丢源码格式。
- 建议建立共享操作契约及类型声明，实际模块拆分以最小改造为准。

验收：同一有效操作经 UI/AI/MCP 入口结果一致；不同投递顺序最终收敛，无法安全合并的情形留下明确冲突；未知扩展字段保留。

### W02 持久提交、操作审计与恢复关联

复用 `src/storage.ts`、已有快照和恢复保护。

- 增加已提交操作、幂等回执和 outbox/接收状态的持久接口；核心一致性见 3.3。
- 记录来源、目标、用户原因、模板版本、前后基线、已接受组和恢复点，不持久化密钥或重复保存完整模型上下文。
- 把操作历史关联到现有版本历史，必要时增加记录键，不先建设第二套完整历史系统。
- 扩展恢复/撤销的新建文档语义，并保护正在提交、尚待同步或恢复中的附件。
- 保留策略和审计清理与实际恢复能力一致；快照已过期时不能继续显示可恢复按钮。

验收：每个故障注入点均可判断未提交或已提交；重启/回执丢失不重复应用；存储失败保留用户编辑并停止新增 AI/MCP 写入。

### W03 实时 MCP、授权与应用写回

复用 stdio、6 个读工具、8 个写工具与现有固定 IPC 防护；保留旧 File 模式。

- 新增 Live 适配器：stdio → 本机受保护通道 → 主进程 → 可信 renderer → 应用持久状态。通道选型在 M0 冻结，避免双实现。
- “最新内容”定义为本次读取屏障前可安全提交的草稿；刷新标题/主题/备注/Markdown，等待持久保存，查询数据与 revision 同源。
- 中文输入组合中、保存冲突、恢复、格式保护或窗口未就绪时返回忙碌/受保护状态，不强制提交半个输入。
- 默认服务关闭、连接只读；写入需明确授权。按工作区/文档约束读取和影响范围，搜索、入链和模板上下文不得泄露未授权内容。
- `dryRun=true` 返回提案；Live 真实写入进入应用待确认，返回 `applied=false` 和可查询状态。用户接受后提交，不要求 agent 再确认一次。
- 实际主体/会话和客户端自报名称分开记录。授权、连接令牌、发现文件不进入备份、导出或同步。
- 重载、退出、升级或撤权使未确认提案失效；已提交结果可重查。断开不回退到 iCloud 文件写入。

验收：备份关闭时也能读最新；两个客户端竞争有确定结果；过期提案、越权和重复请求不能写坏；实际 MCP 客户端完成读取、预览、批准、状态查询和 UI 刷新。

### W04 差异预览、按操作追溯与安全撤销

复用现有生成/润色保护、撤销入口和 `VersionHistoryDialog`。

- 新增文本及树形差异，展示来源、目标路径、新增/删除/移动/关系与关联影响。
- 支持按依赖组接受/拒绝；应用所选修改一次提交，选择动作本身不改正文。
- 将现有生成/润色从直接改写改为提案输出；Markdown 代码、表格、链接和附件差异有明确定位。
- 现有历史入口增加 AI/MCP 操作来源、结果和恢复关联，可跳回具体主题或查看已删除目标的记录。
- 按 3.5 接入远端变更后的撤销/恢复；复用恢复前保存和并发保护，不重做通用版本历史。

验收：拒绝不改正文；接受结果与预览一致；新建文档和跨文档批次可安全回退；远端后续内容不被本机撤销覆盖。

### W05 五类 AI 操作与模板入口

复用 provider 配置、请求预算、取消、四个既有 MCP prompt 和树/关系操作。

| 操作 | 本版新增行为 | 关键验收 |
| --- | --- | --- |
| 子树总结 | 总结后选择写入备注或新增摘要主题，保留来源定位 | 不默认替换原文；缺依据的信息标待确认 |
| 结构重排 | 提出已有节点的父子/顺序变化 | 节点集合及 id 保留，无环、不漏主题 |
| 去重合并 | 展示保留项、被合并项、字段/子树及引用迁移 | 同名不自动等于重复；跨文档影响需完整授权 |
| 任务拆解 | 新增可勾选任务子节点，复用现有字段 | 不覆写原任务状态，不编造已确认的负责人/日期 |
| 关系建议 | 提出同文档合法端点、方向、标签及理由 | 接受才创建，排除重复/无效关系，树结构不变 |
| 模板执行 | 复用 PRD/任务等定义，补会议纪要；应用内选择参数和落点 | 默认预览后新建文档；来源可追溯、新文档可撤销 |

- UI/MCP 使用共享、版本化的模板定义。新增文档使用新 id，不复制源文档身份。
- 模型只输出允许的结构化候选，不可执行任意脚本、任意 JSON Patch 或扩大权限。
- 默认发送选中内容及必要上下文，不自动上传全库或附件二进制；超限先让用户缩小范围或明确分批。
- 所有操作经过 W04/W02；不为某个 AI 菜单另建写入入口。

验收：五类操作及三类模板入口均有成功、拒绝、部分接受、过期、取消和无效输出用例；实际 provider 完成一条完整流程。

### W06 节点合并与冲突语义

复用现有文档级同步入口和冲突提示，按 M0 选定机制升级合并行为。

| 并发场景 | 本版要求 |
| --- | --- |
| 修改不同节点 | 自动保留两边修改，各副本一致 |
| 同节点修改互不相关字段 | 按已冻结字段规则组合，不能将整节点后写值覆盖另一字段 |
| 同字段修改 | 保留可比较的候选及来源；首版不强求逐字符自动合并 |
| 同一位置插入多个节点 | 顺序稳定且不丢节点，跨设备重复同步不抖动 |
| 同一节点移动到两个父级 | 明确冲突或有记录的稳定规则，不能出现双父级 |
| 并发移动形成环 | 阻止非法结构，保留冲突证据及可恢复内容 |
| 删除与编辑/新增子节点竞争 | 不静默丢失编辑，不无提示复活删除内容；进入定义好的冲突处理 |
| 文档删除与离线设备重连 | tombstone 与新编辑有明确处理，不把旧副本当新文档自动上传 |
| 合并、改名与链接/关系变动 | 引用身份与实际结果一致，多文档批次完整处理 |
| 同步重复、乱序、断连 | 已应用操作不重复执行，缺依赖先等待/补齐，不猜测结果 |

验收：双客户端、离线后重连及可重复乱序投递均通过；内容和结构收敛，无法自动处理的冲突可定位、可恢复。

### W07 增量同步、checkpoint 与可靠重试

复用现有 Sync Server、鉴权、SQLite、文档清单和 operation log 基础，新增的是完整的同步应用协议。

- 冻结版本化操作包、因果/基线信息、幂等键、游标与能力协商；现有 API 仅追加日志的行为不能直接当作提交成功。
- 本机 outbox 持久排队，收到服务器持久确认才标记上传完成；远端接收事务成功才推进本机游标。
- 操作包分页、有界读取、重试退避，可处理重复、乱序、消息缺口、服务器重启及离线积压。
- 传输以变化数据为主；首次接入或缺少可用增量时取得已校验 checkpoint，再追赶后续操作。
- 日志压缩和 tombstone 清理必须有保留/确认策略。落后设备不能靠旧游标悄悄复活已删除内容；需要重建基线时先保护其未同步修改。
- 文档快照、操作流与服务端确认状态的原子边界在协议中明确，避免出现“有日志但正文不同步”或相反情况。
- 导出/导入和更换设备后副本身份不冲突；已有同步空间的旧协议客户端按 W10 处理。

验收：网络中断、确认丢失、重复上传、缺页、日志裁剪后的离线设备都可正确恢复；固定编辑样本的传输量证明使用增量，不能仍每次传整库却只改名称。

### W08 节点冲突界面与同步历史

复用文档定位、差异展示和历史恢复入口，不新增第二套编辑器。

- 节点级冲突展示当前值、候选值、来源设备/操作及必要共同基线；可选其中一项或手工整理后提交。
- 冲突解决写入正常操作流，具备基线校验、审计与恢复；不能直接修改服务端数据库绕开客户端。
- 同步历史按文档/批次展示本机、远端、自动合并、冲突处理及失败状态，关联实际操作 id。
- 本机敏感审计和模型上下文不因展示同步历史而全部上传；只交换必要来源及变更信息。
- 历史恢复产生新的操作并尊重远端后续修改，保留旧历史，不倒退同步游标。

验收：两台设备能看到相同已解决结果；再次发生冲突有明确提示；来源、批次和恢复内容一致，过期恢复点显示准确。

### W09 附件二进制同步与生命周期

复用 1.7.0 的 SHA-256 身份、原始文件、格式校验、本机清理和 ZIP 补齐。

- 在现有 Sync Server 范围内增加受鉴权的对象存在性、上传/续传、下载和完整性确认；路径由 assetId 派生，拒绝任意文件路径。
- 流式计量与哈希校验，临时文件完成后原子安装；同内容复用，损坏对象不覆盖可用副本。
- 为断网、重启和中途取消保存有界传输状态，恢复后继续或安全重试；限制并发、单文件、批次与服务端磁盘占用。
- 正文/元数据可先到达，图片明确显示待下载、缺失或失败；所有必需对象校验完成后才显示“附件同步完成”。
- 本机恢复、历史、回收站、outbox 和在途传输共同保护对象；复用现有扫描根并补新增来源。
- 远端删除与清理考虑活跃文档、保留恢复点、上传租约和离线设备。未形成可靠保留规则前默认保守保留，不按本机 30 天隔离规则直接删除远端对象。
- 服务端配额满时保留本机原件和待传状态，提供明确诊断；不能因上传失败回收本机附件。
- iCloud 完整备份继续使用既有顺序与外部变更保护，附件同步不替代备份。

验收：两台设备无需手工 ZIP 即可取得原始附件；哈希一致，断线/取消/空间不足不损坏原件；删除、撤销、历史恢复及旧设备重连不导致活跃附件丢失。

### W10 迁移、旧客户端和 File MCP 兼容

复用现有格式校验、ZIP、旧客户端保护和外部备份载入。

- M0 冻结正文格式、同步协议、导出格式和最小可写版本。不能同时沿用旧“无需迁移”的假设又新增旧客户端无法保留的因果信息。
- 首次升级前固定并保留可验证的完整工作区 ZIP；迁移保持文档/主题 id、链接、关系、附件、回收站和 Markdown。迁移失败保留旧数据。
- 先升级 Sync Server，再接入 2.0 客户端；服务端记录空间/文档能力要求，并在事务内拒绝旧协议覆盖。旧端受保护读取或明确提示升级，不静默丢元数据。
- 原 File MCP 参数、锁、CAS 和快照继续可用于受支持的旧格式文件；若新格式无法安全写入，则只读或明确拒写，不能为兼容旧脚本而剥离同步信息。
- File 写入只补操作与现有快照的关联。外部 JSON 不携带可信的当前因果状态，载入时视为显式导入/恢复并生成新操作，不把其旧日志直接重播。
- 普通 JSON、Markdown、完整 ZIP 和诊断/恢复导出的携带范围分别说明；同步身份、设备私有状态和服务凭据不随普通副本复制。
- alpha/beta 数据默认隔离，用户选择使用真实数据前完成备份和迁移提示。回到 1.7.0 走已验证的导出/恢复路径，不假设旧应用能打开升级后的数据库。
- Web 保持维护边界；涉及未知格式或新同步空间时保护旧写入口，部署包包含所需契约模块。

验收覆盖旧端/新端、旧服/新服、v1/v2 导入、升级中断、外部文件写回、ZIP 空白环境恢复和降级导出；未知协议不写坏现有数据。

## 6. 资源预算与性能样本

现有预算继续有效：工作区 JSON 64 MiB、AI 请求 90 秒/响应 2 MiB、附件单文件 128 MiB；图片与 ZIP 沿用 1.7.0 规则。新操作包、outbox、远端日志、checkpoint、附件续传块及服务器配额在 M0 根据样本冻结，集中定义，不能各端各设一套。

- AI 上下文与提案采用有界节点/字节/命令数；超限明确缩小范围或分批，不静默截断。
- 同步分页、重试和离线积压都必须有界。日志清理与 checkpoint 配套，保留仍未确认或待处理的本机修改。
- 审计沿用可解释的保留策略，过期状态与恢复数据一致；不增加未经验证的固定大容量历史库。
- 附件流式传输限制内存和并发，取消后释放句柄及临时资源。服务器配额和磁盘失败可诊断。
- 固定样本包含 100 文档/20,000 主题、单文档 20,000 主题/200 次编辑、大批量提案、双端并发移动、长期离线追赶、重复投递，以及重复附件/大文件/损坏对象。
- 记录读屏障等待、差异首屏、确认到持久回执、双端收敛、增量字节数、日志增长、附件吞吐、GC 后 heap/RSS 和重启恢复时间。
- 与同环境 1.7.0 基线比较；纯文本编辑/搜索或稳定内存退化超过 20% 时进入门禁复核。新增同步指标由 M0 原型实测后设目标，不将模型响应耗时混入本机提交性能。

## 7. 组合验收矩阵

| 场景 | 必须观察的结果 |
| --- | --- |
| 自动备份关闭、输入未失焦 | Live 读到屏障前已提交内容，revision 与内容一致 |
| 中文组合输入、Markdown/备注草稿 | 不丢字、不强制提交半成品；忙碌/冲突可诊断 |
| 拒绝提案、部分接受、生成取消 | 只应用被接受且依赖完整的组，一次撤销对应一次提交 |
| 等待审批时另一设备改目标 | 旧预览失效并重新比较，不自动批准新内容 |
| 两个客户端提交、相同请求重试 | 权限与基线有效才提交；重复消息不重复创建 |
| 提交前/后崩溃、回执丢失 | 正文、审计、outbox 和回执一致，重启可定位结果 |
| 不同节点/字段并发修改 | 按冻结规则组合并收敛，双方修改保留 |
| 同字段、并发移动、删除对编辑 | 冲突有位置和候选，树不成环、不静默丢失 |
| 本机撤销发生在远端修改之后 | 远端内容保留；冲突时提供明确选择 |
| 离线积压、缺页、乱序及重复投递 | 可续传、可补齐依赖，游标只在落盘后推进 |
| checkpoint 之后旧设备重连 | 未同步编辑先保护，旧 tombstone 不被无意复活 |
| 跨文档改名/合并批次 | 入链、关系和身份一致，未完成批次不被标成完整结果 |
| 附件先有引用、后到字节 | 状态准确，完整校验前不声称附件已同步 |
| 上传/下载中断、空间不足、坏哈希 | 原件安全、重试有界、损坏对象不安装 |
| 删除/撤销/历史恢复与远端清理竞争 | 可恢复正文对应的附件仍受保护 |
| File 外部写入与自动备份 | 继续暂停保护；显式采纳生成新操作且保留来源 |
| 旧客户端/旧服务接入新空间 | 明确升级或受保护状态，不覆盖新协议数据 |
| 1.7.0 迁移中断、ZIP 恢复、回退 | 原数据可恢复，身份和附件完整，降级边界明确 |
| 五类 AI 与三类模板 | 来源可追溯、输出有界、接受结果可撤销，缺依据内容标待确认 |
| 全部断网/服务关闭 | 本机核心编辑与已下载附件继续可用，不强迫依赖服务器 |
| 隐私与授权 | 普通同步/导出不含密钥、令牌、私有配置或完整模型上下文 |

## 8. 正式发布门禁

2026-11-10 用户确认的验收调整适用于本次开发交付。真实 AI/provider、用户 MCP 客户端和两台物理设备的测试转交用户后续补测，相关实机手工场景继续列在验收记录中。以下原门禁中的这些项目已按本次确认延后。

以下任一项未满足，2.0.0 仍属于预发布：

- R01–R14 未完成，或范围变动未明确记录。不能以原 1.8.0 功能完成代替合并版本完成。
- 出现静默覆盖、重复执行、数据不收敛、结构成环、旧端破坏新数据、虚假成功或不可解释的附件丢失。
- 审批、提交、合并、撤销、恢复和旧数据迁移的边界没有故障证据。
- 最终打包应用的关键流程未验证。两设备离线并发与实际 MCP/provider 按上述用户确认转为后续补测。
- 同候选工程检查、性能复核、最终制品摘要与发布说明未完成。

正式签名/新架构若后续加入交付承诺，补对应门禁；沿用 ad-hoc 则继续披露首次安装及自动替换限制。文件夹、XMind、Intel/Universal、分享页等不会因合并而自动成为 2.0.0 的隐含阻断项。
