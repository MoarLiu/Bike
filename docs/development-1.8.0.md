# Bike 1.8.0 开发计划（已合并至 2.0.0）

整理日期：2026-11-09（Asia/Shanghai）

**归档说明：用户于 2026-11-09 确认将 1.8.0 与原 2.0.0 的需求合并，统一开发并以 2.0.0 为正式发布目标，不再单独发布 1.8.0。现行范围、架构、里程碑和验收以 [2.0.0 开发计划](development-2.0.0.md) 为准。**

下文保留合并前的需求分析供溯源。其中“节点自动合并/附件同步不在本版”、独立 M0–M6 里程碑和旧估算均为历史边界，不再约束合并版本，也不代表已完成实现。

归档时状态：需求细化与实施建议，尚未实施。原版本主题为 **AI 与 MCP 闭环**：agent 读取应用中的最新已提交内容，AI/MCP 提出的修改经预览、确认和并发校验后提交，用户能够追溯来源并安全恢复。

产品定位沿用本地优先的个人知识工具，以 Electron macOS 桌面版为主。本文中的新增接口、模块、预算和人日均为规划建议，M0 验证后冻结；现有能力与本版待实现能力分开记录。

### 1.2 当前实现对本版的约束

| 已核对的实现 | 主要位置 | 本版要解决的问题 |
| --- | --- | --- |

| AI 仅有生成/润色，结构化结果直接写入主题，Markdown 结果直接改草稿；已有取消及过期结果保护 | `src/ai.ts`、`src/App.tsx` | 保留现有保护，将两种入口统一改为“生成提案 → 差异预览 → 选择接受 → 提交” |

## 2. 目标、范围与用户路径

### 2.1 版本完成后应能做到

1. Bike 已打开且获授权时，agent 直接读取当前工作区；无需先启用或等待 iCloud 备份。
2. AI 和 MCP 修改都能看到来源、目标、逐项差异和关联影响，用户确认前不改变正文。
3. 接受结果通过统一操作层提交，具备写前恢复点、持久审计、并发校验和撤销能力。
4. 子树总结、结构重排、去重合并、任务拆解、关系建议均能形成可选择的提案。
5. PRD、任务和会议纪要模板可在应用内和 MCP 使用，生成内容保留来源定位。
6. 重启后仍能找到已完成操作及恢复入口；恢复不会静默覆盖该操作之后的编辑。

核心纵向切片：

> 修改主题并保留输入焦点 → MCP 读取包含该修改的已提交内容 → 提交改写预览 → 应用内接受 → 四视图刷新 → 撤销/重做 → 重启 → 审计定位 → 恢复。

### 2.2 本版范围边界

| 事项 | 本版边界 |
| --- | --- |

## 3. M0 冻结的架构与行为

### 3.1 数据源与传输

保留现有 stdio MCP 入口及 File 存储实现，只新增 Live 适配器，明确区分两种来源：

- **Live 适配器**：stdio MCP → 本机受保护通道 → Electron 主进程 → 可信 renderer 的提交协调器 → IndexedDB。
- **File 既有实现**：stdio MCP → 显式配置的 JSON 文件及 `.backups`，复用 `WorkspaceStore` 的文件锁、CAS、写前快照与原子替换。

首选在 macOS 用户私有目录中使用本地 socket 连接 stdio 适配器与主进程；M0 验证正式包、权限、路径长度、重连和安装路径变化。若改用 loopback HTTP，必须重新冻结端口、认证、Origin/Host 校验及浏览器跨站访问防护。两条传输路线本版只实现一条，不同时维护两套服务。

实时服务默认关闭；用户在应用中启用后提供连接配置和状态。认证信息与发现文件只保存在用户私有目录，权限受限，支持撤销与轮换，不进入工作区、同步、ZIP 或普通日志。能力清单、工作区实例 id 与桥接协议独立版本化，不能只用窗口 id 或文件路径识别工作区。

正文权威仍是应用现有的 IndexedDB。主进程负责认证、路由及请求管理，不另存一套可以独立修改的正文；新桥使用固定 IPC 接口和可信 sender 校验，不接受任意脚本、数据库查询或路径参数。

### 3.2 “最新内容”的明确语义

默认读取的是**本次读取屏障之前可安全提交的最新内容**：

1. 在拥有该工作区的可信窗口刷新标题、主题、备注和 Markdown 草稿。
2. 等待保存完成，从同一已持久化版本构建查询快照；返回数据和 revision 必须属于同一快照。
3. 正在中文输入法组合输入、存在保存冲突、恢复、格式保护或窗口未就绪时，返回可诊断的忙碌/冲突结果，不终止组合输入或冒充最新版本。
4. 读取期间继续产生的编辑属于下一次版本。长查询固定读取版本，后续读取再获取更新。
5. 显式请求“上次保存版本”时可返回旧版本，但必须携带 `freshness=last-saved`、保存时间和草稿状态；文件模式始终标注 `source=file`。

`dryRun` 不应用所提议的正文修改；为取得读取基线而完成用户既有草稿的正常保存，应与提案修改明确区分。权限过滤先于内容返回，未授权文档不能通过全文搜索、摘要、反向链接或模板上下文泄露。

建议响应携带 `source`、`workspaceId`、不透明 `revision`、`savedAt`、`freshness`、`hasPendingDrafts` 和能力版本。Live revision 绑定工作区实例、会话代际、持久 revision 及内容基线；文件 SHA-256 不直接当作 Live token 使用。

应用退出、renderer 崩溃或重载时，Live 返回不可用并废弃未确认提案，不自动读取或写回 iCloud 文件。已持久提交的回执可在重新连接后查询；未提交任务不会在重启后自行执行。

### 3.3 统一操作与提案

共享层负责本版提案所需的命令调用、校验、差异与影响计算，存储适配器负责提交。直接复用已有树、知识连接、MCP 写入规则；只抽取 Live/AI 共用的部分，不把全量命令重构、重写所有视图或重做整个保存层设为开工前提。

| 字段 | 规划含义 |
| --- | --- |
| `schemaVersion`、`proposalId` | 提案契约版本与不可变提案标识 |
| `workspaceId`、`source`、`baseRevision` | 目标数据源和读取基线 |
| `requestId` | 提交幂等键，绑定客户端、工作区及请求内容 |
| `origin` | `ui-ai`、`mcp-live`、`mcp-file`、`external-file-import` 或 `restore` |
| `operations`、`groups` | 明确的命令及不可拆分的依赖组 |
| `affectedDocumentIds`、`affectedNodeIds` | 由应用计算的实际影响范围，不采信调用方声明 |
| `proposalHash`、`expiresAt` | 规范化后的提案摘要与有效期，审批绑定该版本 |
| `context` | 模板 id/版本、provider/model、用户原因、来源节点；均不包含密钥 |

首批命令覆盖已有 8 个 MCP 写工具，并增加本版需要的子树重排、显式合并映射及关系创建。拒绝任意 JSON Patch、任意字段写入和未知命令。id、顺序、时间、影响范围及元数据由应用校验；新增 id 在提案形成时固定，确认时不重新生成。实际提交时间由可信运行时生成，调用方时间不能冒充审计时间。

预览校验树无环、id 唯一、目标存在、顺序合法、字段及资源预算、链接/关系/附件保真。跨文档改名联动、合并后的引用改绑属于同一依赖组；任一受影响文档未获授权时拒绝该组，不悄悄跳过。

1.8.0 采用保守的 revision 再校验。审批后基线变化，提案进入 `stale`，重新读取并生成差异后才能再次确认；不静默重放旧提案，也不引入节点级自动合并。

### 3.4 授权与 MCP 调用流程

以下应用内审批流程用于新增 Live MCP；File 模式沿用现有约定，见 B05。两者的授权来源须分别记录，不能把文件模式的写入请求标记成应用内人工批准。

- 全局服务启用、客户端获准连接、文档读取授权、写入授权、具体提案确认分别检查。默认只读，写入不能仅凭一个模型参数开启。
- 授权可按工作区/文档限定，创建新文档单列能力；创建后将新文档纳入该次授权的规则须显式说明。暂停服务或撤销授权后，排队及待确认写入立即失效。
- 客户端名称是展示信息；审计同时记录应用分配的授权主体/会话标识，不把自报名称当作已验证身份。
- MCP 现有读工具、资源及 prompt 尽量保持名称。现有写工具保留 `dryRun=true` 默认与 `expectedRevision`，Live 模式增加提案及状态回执。
- `dryRun=true` 返回精确提案及确认参数；`dryRun=false` 提交同一提案进入应用审批。缺少已有提案的旧调用可生成待确认提案，不能直接落盘。
- 默认由用户在应用内接受所选差异后完成提交。MCP 立即得到 `pending_confirmation`、`applied=false` 和操作 id，调用方通过拟新增 `get_operation_status` 查询结果，不长期占住工具调用。
- 一次应用内确认即可触发提交，无须 agent 再发送第二次确认。用户拒绝或提案过期后，状态明确结束；agent 不得用重试绕过拒绝。
- 本版不增加“永久信任所有写入”的自动执行模式。审计、配置、备份及恢复副本不通过普通正文读取权限自动开放。

状态至少区分 `previewed`、`pending_confirmation`、`committing`、`committed`、`rejected`、`cancelled`、`stale`、`expired`、`failed`。`applied=true` 只对应持久提交成功。取消发生在提交后时返回已完成结果和恢复入口，不能声称取消成功。

### 3.5 原子提交、幂等与故障恢复

**Live/应用内 AI 的必要增量**：已有 IndexedDB CAS 和历史快照都继续使用；新增的是操作记录、确认回执与恢复点必须一致。建议在现有 `bike-db` 的提交事务中增加必要记录键，保持旧历史库和界面可用。是否需要保存新的恢复正文由 M0 原型决定，不能先假定要建设第二套完整版本历史系统；若增加 store 或提升数据库版本，再明确旧标签页阻塞与回退规则。

完整提交流程：

1. 取得提交队列位置，刷新草稿，重验权限、提案摘要、有效期及当前 revision。
2. 计算选中依赖组的候选状态，验证受影响文档及恢复预算；准备操作恢复副本和附件保护集合。
3. 在同一 IndexedDB 事务内做 CAS 并写入正文、恢复记录、操作状态和幂等回执。事务中不等待网络、文件系统或用户确认。
4. 事务成功后发布同一提交结果到 UI/索引/撤销栈，触发既有备份与同步调度，最后向 MCP 报告成功。该临界段与普通保存、撤销、同步采纳共用协调器；期间新输入保留为后续草稿，不能被已提交快照覆盖。
5. UI 通知失败或回执丢失时，持久记录仍是准据；重连先查询回执，不再次应用操作。原有自动保存队列必须识别新基线，不能把旧内存覆盖回来。

关键失败必须整体停止：恢复副本写不下、审计记录写失败、CAS 不匹配、格式未知，均不得只写正文。Live AI/MCP 事务失败不走“仅 localStorage 备用副本但仍报成功”的降级路径；用户普通编辑继续保有原来的备用副本保护。

同一 `requestId` 与相同请求摘要重试返回原结果；相同 id 携带不同内容则拒绝。已完成记录的幂等检查在会话过期判断之前进行，避免提交成功、桥重启后错误重做。过期或被清理的幂等键也不能把未知结果当作可安全重放。

### 3.6 兼容与回退

- 本版审计、授权、提案和恢复元数据作为本机独立格式，默认不提升正文 Workspace v1/v2，不进入 Sync 或常规正文导出。
- 不改变已有附件 schema、稳定链接 id 和同文档关系格式。遇未知扩展字段保留原值；无法证明安全的操作拒绝执行。
- 既有 `bike-history-db` 继续可读。新增操作恢复记录由统一查询入口呈现，但不得假定它与正文数据库能跨库原子提交。
- 回退到 1.7.0 前导出完整工作区 ZIP；纯文本可另存 JSON。若新增 IndexedDB 版本使旧应用不能直接读取，必须提供经验证的导出/恢复路线，不宣传“直接降级无影响”。
- 回退后旧版本不了解新增恢复记录，可能无法保护其中独有的附件。因此降级前需导出需保留的恢复点或完整本机恢复包，并说明旧版附件清理风险。
- 新增模块必须进入 Electron 包和独立 MCP/部署包；正式包从含空格/中文的安装路径启动，并验证升级后配置与本地桥重连。

### B07 五类 AI 知识操作

这里的增量是应用内可执行、可预览、可写回的知识操作。总结、任务和结构审查的 MCP prompt 已存在，关系线、树移动及任务字段也已有实现，不计作重建。

所有能力复用上下文选择、请求预算、schema 校验、提案预览及提交，不各自新增写入通道。

源文档、模板变量和模型输出均按内容数据处理。模型不能通过正文指令或返回字段扩展授权、读取范围、执行脚本或绕过审批；来源中的指令性文字也不能成为新的工具权限。

| 能力 | 默认输入与落点 | 必须保留/提示 | 验收场景 |
| --- | --- | --- | --- |
| 子树总结 | 选定子树；预览后选择写入备注或新增“摘要”子主题 | 来源主题定位；事实与待确认信息分开，不默认替换原文 | 深层、任务、备注混合子树，摘要可追溯并撤销 |
| 结构重排 | 当前文档选定子树；只调整已有节点父子及顺序 | 现有 id 和全部内容保留；不得成环、漏节点或凭空合并 | 移动前后节点集合相同，链接/附件/任务不丢失 |
| 去重合并 | 当前子树的候选重复项；逐组确认 | 展示保留节点、被合并节点、字段冲突、子节点及引用迁移 | 同名异义不自动合并；存在入链时全部显式处理或阻断 |
| 任务拆解 | 选定主题/子树；新增任务子节点 | 现有任务状态不覆写；负责人/日期无依据时标待确认，不引入新任务系统 | 多层任务可勾选、可逐组拒绝、可整体撤销 |
| 关系线建议 | 当前文档中用户选定的内容 | 输出合法端点、方向、标签与理由，排除重复/无效关系，不改变树 | 接受后脑图显示关系，大纲层级不变，撤销移除 |

去重的“内容相近”由模型建议，是否合并由用户决定。合并导致跨文档入链改绑时升级为显式跨文档依赖组；未获完整授权则保留候选但禁用提交。结构重排与去重是不同操作，不以重排入口隐藏删除。

- 展示可恢复期限、占用、已过期状态和导出/清理入口。过期记录只可追溯，不显示仍能恢复的按钮。

验收：重启后按来源找到写入并恢复；后续编辑不被无提示覆盖；多文档恢复整体成功或整体失败；附件、链接和 Markdown 保真；恢复操作可再撤销。

## 5. 资源预算、保留与性能

下表是 M0 待验证的初始建议，不是已经实现的限制。应在共享契约中集中定义，避免 UI、MCP 和主进程各用一套数值。

| 项目 | 建议初始值或沿用值 | 超限/失效行为 |
| --- | --- | --- |
| AI 请求 | 沿用 90 秒超时、2 MiB 响应上限 | 可取消，超时/超限不提交，保留当前编辑 |
| 默认 AI 上下文 | 1,000 个主题且正文合计不超过 64 KiB | 显示实际范围，要求缩小范围或显式分批，不静默截掉后半段 |
| 单个提案 | 最多 200 条命令、1,000 个受影响主题、2 MiB 命令载荷 | 提交前拒绝；不可拆分依赖组不得以分批方式绕过 |
| 全局正文预算 | 沿用 64 MiB 及现有主题/深度校验 | 沿用受保护读取与错误提示 |
| 同时写入 | 每工作区一次持久提交；等待确认提案最多 10 个 | 有界排队、返回忙碌，拒绝的任务不自动无限重试 |
| 提案有效期 | 15 分钟，或基线/权限/会话变化时提前失效 | 重新生成预览；重启不自动继续旧审批 |
| 操作恢复数据 | 复用对应历史/文件快照保留策略；必要的提交中保护与新增记录预算由 M0 实测 | 快照过期时同步标记不可恢复；新写入不能在必要恢复记录保存失败时继续 |
| 审计摘要 | 分页与有界存储，具体条数/字节上限待增量样本验证 | 与恢复记录生命周期一致；容量不足明确提示 |
| Live 幂等记录 | 覆盖对应有效请求与恢复记录；过期 token 不重新执行 | 已清理结果返回结果已过期/未知，不据此重做 |

恢复期承诺以界面可见的保留策略为准。用户显式清理时说明将失去哪些恢复能力，先提供导出；状态未核清、待决或仍在保护期内的记录不作为普通过期垃圾处理。导出恢复点必须携带其引用附件，不能只导出 JSON 后声称可完整恢复。

固定样本沿用 100 文档/20,000 主题、单文档 20,000 主题/200 次编辑，并增加 200 命令差异、跨文档入链、含图子树、连续 1,000 次幂等重试及审计分页。

记录屏障等待、查询 p95、差异首屏、确认到持久回执、重启恢复、GC 后 heap/RSS 和磁盘增长。建议普通 200 主题读取与差异首屏 p95 各以 500 ms 为初始目标，不含模型耗时及人为审批；M0 用同机实测冻结。纯文本搜索和编辑较已核验 1.7.0 基线退化超过 20% 时进入门禁复核，不能仅以总体测试通过放行。

## 6. 按增量推进的里程碑与估算口径

| 阶段 | 核心工作 | 完成出口 | 工作性质 |
| --- | --- | --- | --- |
| M0 增量原型 | 确认复用边界，验证 Live 读取与操作记录提交 | 只列必须新增/改造的代码，冻结最小方案与验收用例 | 风险验证，不重做前版验收 |
| M1 现有命令与保存接入 | B01/B02，B09 恢复关联 | 补操作审计、幂等和新建文档撤销，复用现有编辑与历史 | 必要改造 |
| M2 实时 MCP 切片 | B03/B04，B05 调度联调 | 备份关闭时读最新；应用批准后写回和 UI 刷新 | 核心新增 |
| M3 差异与追溯体验 | B06/B09，生成/润色入口改造 | 逐组接受/拒绝、按操作查来源并恢复 | 核心新增 + 旧入口扩展 |
| M4 AI 能力与模板 | B07/B08 | 五类操作、PRD/任务应用内执行、新增纪要模板 | 新增工作流 + 复用 prompt |
| M5 兼容收口 | B05 审计关联与定向回归 | 旧客户端、外部载入、备份、Sync 和附件保护不退化 | 小幅改造 + 回归 |
| M6 候选验收 | B10、性能与故障演练 | 新链路证据齐全，既有脚本回归通过 | 验证与发布准备 |

撤回初稿的 **38–55 人日 / 含余量 46–66 人日**估算：该数字混入了偏大的底座重构、旧文件协议升级和独立恢复机制，未充分扣除已完成能力，不能作为本版增量工期依据。

M0 后按“新增代码、已有入口接入、定向回归、集成余量”分别估算，再给出总工作量与排期。附件库、ZIP、通用撤销、历史面板、旧文件锁/CAS、原有 prompt 不重复计开发人日；回归执行仍计验证成本。现阶段不再用另一个未经验证的较小数字替代旧估算。

关键顺序为 B01/B02 → B03/B04 → B06/B09 → B07/B08 → 完整验收。B05 的接口及失败语义从 M0 开始，关键互操作在 M2 就验证，M5 完成全部兼容证据。不得先做五类 AI 菜单，再补提交与恢复基础。

最先完成的端到端样例只需一个主题改字和一次新建文档，但必须覆盖批准、保存回执、UI 更新、撤销、重启后恢复和重复请求；不能用单独的 socket ping 或模型成功返回代替。

## 7. 验收矩阵

| 场景 | 必须观察的结果 | 验证层级 |
| --- | --- | --- |
| 自动备份关闭、主题/备注未失焦 | MCP 读取屏障完成后取得本次已提交修改，来源为 Live | Electron + 实际客户端 |
| Markdown 草稿与中文组合输入 | 可提交草稿正确刷新；组合输入期间忙碌可重试，不丢字、不强制提交 | Electron 手动 + 自动回归 |
| 保存失败或仅备用副本成功 | Live 写入不报成功，提案不改正文，已有用户编辑有保护 | 存储故障注入 |
| 未授权查询、跨文档入链与搜索 | 不返回范围外正文/标题/摘要，缺权限的原子组不能提交 | 模块 + MCP |
| dry-run、全部拒绝、取消 | 提案不改正文；正常草稿保存与提案修改可区分 | 模块 + 四视图 |
| 逐组接受、依赖组缺项 | 仅已接受且依赖完整的组提交，一次撤销还原整批 | 模块 + UI |
| 预览后继续编辑、Sync 替换或恢复 | 旧提案过期，不覆盖当前内容，重新预览才可确认 | 集成 + Electron |
| 两个客户端同时提交 | 仅匹配当前 revision 的提交成功，另一个明确冲突 | 多客户端测试 |
| 审批后撤销权限/替换 payload | 提交被拒绝，原审批不能复用到另一提案 | 安全用例 |
| 提交各阶段崩溃、回执丢失 | 正文/恢复点/审计状态一致，重启及重试不重复应用 | 故障注入 |
| 新建文档及后续编辑 | 新建可撤销/重做；有后续内容时恢复不直接删除 | 历史 + UI |
| 重排、合并及跨文档改名 | id、链接、关系、附件、备注与任务保真；跨文档整批提交 | 共享契约 + UI |
| 历史操作已有后续编辑 | 展示冲突与恢复为副本；显式覆盖前保存当前内容 | 恢复运行时 |
| 操作恢复点与附件清理 | 受保护附件不被删除；过期/导出/显式清理行为可解释 | 附件模块 + 打包应用 |
| File 外部修改与自动备份 | 暂停且不覆盖；文件审计可查询，采纳到 UI 需要确认 | 文件锁 + Electron |
| File 审计补写前/后崩溃 | 原有文件写入与快照保护不退化；审计能标识完成/失败/未知，不重复执行 | 文件故障注入 |
| 应用关闭、重载、升级、断连 | Live 不自动降级写文件；旧审批失效，已提交结果可查询 | 打包应用 |
| 无效/超大模型输出、超时/取消 | schema/预算拒绝，无部分写入，界面恢复可操作 | fixture + 实际 provider |
| PRD/任务/会议纪要生成 | 可预览、可定位来源、可撤销新建；缺信息标待确认 | 模板 fixtures + UI/MCP |
| 脱敏日志、备份及导出 | 不含 API key、认证令牌、授权文件；导出范围准确 | 静态扫描 + 实物检查 |
| 1.7.0 升级及回退 | v1/v2、附件、ZIP、旧历史可读；回退路线和数据损失边界明确 | 隔离数据目录 |
| 性能与四视图 | 大样本预览有界、无持续内存增长，四视图结果一致 | 固定样本 + 渲染检查 |

确定性自动化负责正确性与故障覆盖；真实客户端、真实 provider、系统输入法和最终打包应用分别保留证据，不能互相替代。

## 8. 发布门禁与范围取舍

以下任一项未完成则不应将版本标为正式交付：

- B01–B06、B09/B10 的安全闭环未通过，或 B07/B08 的范围尚未明确完成/正式调整。
- 任一支持路径会绕过预览/授权、覆盖较新内容、报告虚假成功、重复应用请求，或缺少在保留期内可用的恢复点。
- 正文、审计与恢复数据的崩溃一致性没有证据，或附件清理不能枚举新增恢复根。
- Live 失败后静默降级文件写入，或把文件快照对外描述成最新 UI 内容。
- 新建文档、跨文档联动、Markdown 或历史恢复仍有身份/引用丢失。
- 同候选提交的工程检查、关键运行时、实际 MCP 接入及最终打包制品未验证。

基础命令沿用 `npm run check`、`npm run test:runtime`、`npm run test:electron-runtime`、`npm run test:attachments-runtime`、`npm run test:updates-runtime`；新增 Live MCP/AI 提案运行时命令在开发中加入 `package.json` 后再作为实际门禁执行。不得在验收记录中引用尚不存在或未执行的脚本作为通过证据。

发布前核对最终候选 commit、CI Node/Electron 与本地工具链、实际打包内容、安装路径、摘要和签名状态。沿用当前已确认的 arm64/ad-hoc 分发边界时如实披露限制；若改变签名、架构或自动更新承诺，另行补齐相应实机门禁。

如需缩小首版范围，优先顺延模板自定义、额外 provider 适配、更多关系类型或更大批量预算；不得删去审批、并发校验、持久回执、审计、恢复和附件保护来换取菜单数量。路线图内五类 AI 能力及三类模板的删减须显式记录。
